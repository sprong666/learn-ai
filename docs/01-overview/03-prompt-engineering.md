# 提示词工程

> 提示词设计的原则、模式与实战技巧

## 本章目标

- 掌握有效提示词的六大构成要素
- 学会用 CRISPE、RTF 等框架系统化地写提示词
- 知道什么时候需要完整结构、什么时候一句话就够

## 一、有效提示词的六大构成要素

可以把提示词的组成要素想象成乐高积木：不需要每次都用全，但知道有哪些，就能按需搭建。一个完整的提示词通常包含：

```
角色（Role）      你是一名资深软件工程师
上下文（Context）  正在开发一个 React 应用
任务（Task）      审查这段代码的缺陷
约束（Constraints）只关注安全问题
格式（Format）    以编号列表返回结果
示例（Example）   例如：第 42 行存在 SQL 注入风险
```

### 1. 角色（Role / Persona）

设定角色能让模型从特定专业视角组织回答。角色会"预热"模型：使用恰当的词汇、调用相关领域的知识、保持一致的视角、照顾目标读者。

| | 提示词 |
| --- | --- |
| 无角色 | 解释量子计算。 |
| 有角色 | 你是一位擅长把复杂概念讲得通俗易懂的物理学教授。请解释量子计算。 |

常用角色句式：

```
"你是一名有 X 年 [领域] 经验的 [职业]"
"扮演一个 [角色]，特点是 [特征]"
"你是一位 [领域] 专家，帮助 [某类读者]"
```

### 2. 上下文（Context / Background）

模型对你、你的项目、你的目标**一无所知**，除非你告诉它。

| | 提示词 |
| --- | --- |
| 弱上下文 | 修复我代码里的 bug。 |
| 强上下文 | 我在用 Node.js + Express 开发 REST API，用 JWT 做用户认证。用户访问受保护路由时，即使 token 有效也报 403。相关代码如下：[code] |

上下文应包含：

- **项目详情** — 技术栈、架构、约束
- **当前状态** — 试过什么、什么有效、什么无效
- **目标** — 最终想达成什么
- **限制条件** — 时间、技术要求、风格规范

### 3. 任务（Task / Instruction）

任务是提示词的核心——你到底想让模型做什么。要具体、无歧义，按"模糊 → 好 → 最好"的阶梯打磨：

> 模糊：修改这篇文章
> 最好：修改这篇文章的语法和表达，保持原有语气，但把篇幅压缩 20%

好用的动词按类别挑选：

| 类别 | 动词 |
| --- | --- |
| 创作 | 写、创作、生成、设计 |
| 分析 | 分析、评估、对比、评审 |
| 转换 | 转换、翻译、重排、总结、扩写 |
| 解释 | 解释、描述、澄清、举例说明 |
| 解决问题 | 解决、调试、修复、优化 |

### 4. 约束（Constraints / Rules）

约束用于框住输出，防止跑偏：

- **长度**："200 字以内"、"正好给 5 条建议"、"写 3-4 段"
- **内容**："不要包含代码示例"、"只关注技术层面"、"避免营销话术"
- **风格**："用正式的学术语气"、"像给 10 岁孩子讲解一样"
- **范围**："只考虑 Python 3.10+ 可用的方案"、"只限免费工具"

### 5. 输出格式（Output Format）

指定格式能直接得到可用的结构化结果：

```
"以无序列表返回"
"返回 JSON，包含字段：title、description、priority"
"按以下结构组织：## 摘要 / ## 要点 / ## 建议"
```

JSON 输出示例：

```
分析这条用户评论并返回 JSON：
{
  "sentiment": "positive" | "negative" | "neutral",
  "topics": ["主要话题数组"],
  "rating_prediction": 1-5,
  "key_phrases": ["值得注意的短语"]
}

评论："产品到货很快也很好用，但说明书让人困惑。"
```

### 6. 示例（Few-Shot Learning）

示例是让模型明确"到底要什么"的最强手段：

```
把下面的句子转成过去时。

示例：
输入："She walks to the store"
输出："She walked to the store"

现在转换：
输入："They run every morning"
```

少样本（Few-Shot）分类示例：

```
按紧急程度给支持工单分类。

示例：
"我的账号被盗了" → Critical
"怎么改密码？" → Low
"支付失败但被扣款了" → High

分类："打开设置时应用崩溃"
```

### 组合示例：六要素齐备的完整提示词

```
# 角色
你是一名有 10 年经验的资深技术文档工程师。

# 上下文
我在为一个支付服务的 REST API 写文档，读者是把 API 集成到自己应用里的开发者，
有中级编程水平，但可能不熟悉支付业务。

# 任务
为下面这个"创建支付意图"的接口写文档。

# 约束
- 语言清晰简洁
- 包含常见错误场景
- 不透露后端实现细节
- 假设读者懂 HTTP 和 JSON 基础

# 输出格式
1. 接口概述（2-3 句）
2. 请求（方法、URL、header、body 示例）
3. 响应（成功和错误示例）
4. 代码示例（JavaScript/Node.js）

# 接口详情
POST /v1/payments/intents
Body: { "amount": 1000, "currency": "usd", "description": "Order #1234" }
```

## 二、不是每个提示词都需要六要素

简单任务一句话就够：

```
把 "Hello, how are you?" 翻译成西班牙语。
```

以下情况才需要叠加更多要素：

- 任务复杂或有歧义
- 需要特定输出格式
- 结果不符合预期（要素是"调试提示词"的抓手）
- 多次查询需要保持一致的风格

## 三、常用提示词框架

### CRISPE

| 字母 | 含义 | 示例 |
| --- | --- | --- |
| C | Capacity/Role（能力/角色） | 你是有 15 年美妆品牌经验的资深营销顾问 |
| R | Request（请求） | 创建下个月的社交媒体内容日历 |
| I | Information（背景信息） | 我们向 25-40 岁女性销售有机护肤品，品牌语气友好且有教育性 |
| S | Situation（情境） | 15 号新品维生素 C 精华上市 |
| P | Persona（风格） | 轻松、多用 emoji、重教育轻推销 |
| E | Experiment（要求实验） | 按周给出内容计划，每周 3 篇 |

### RTF（Role-Task-Format）

轻量三件套，适合日常快用：

```
角色：你是一位擅长把概念讲简单的耐心数学家教。
任务：解释什么是分数、怎么把分数相加。
格式：
- 从生活实例开始
- 用简单语言（不用术语）
- 给 3 道带答案的练习题
- 300 字以内
```

## 小结

- 好提示词是**搭出来**的，不是碰运气碰出来的：角色、上下文、任务、约束、格式、示例六块积木按需组合
- 模型对"你"一无所知——上下文自己给足；任务动词要具体；约束框住输出；示例胜过千言描述
- CRISPE 适合复杂营销/内容场景，RTF 适合日常轻量使用
- 简单任务不必过度结构化，结果不对时再逐个要素"调试"
