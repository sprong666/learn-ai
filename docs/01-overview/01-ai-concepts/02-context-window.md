# 上下文窗口

> 模型能"看到"多少内容，上下文如何被消耗，超长怎么办

## 本章目标

- 理解什么是上下文窗口，它为什么相当于模型的"短期记忆"
- 理解上下文是如何被消耗的（提示词和回答都占空间）
- 掌握长上下文场景下的实用策略

## 一、什么是上下文窗口

**上下文窗口（Context Window）** 是模型在一次对话中能"记住"的内容上限，相当于 AI 的**短期记忆**。它以 Token 计量（Token 概念见 [LLM 与 Token](01-llm-and-token.mdx)）。

关键点：**窗口里装的不只是你的问题，还包括模型的回答、系统提示词、注入的文档等全部内容**：

```
上下文窗口
├── 系统提示词（System Prompt）
├── 你的提示词（Prompt）
├── 注入的参考资料（文档、检索结果……）
└── 模型的回答（Response，逐 Token 生成，边生成边占用）
```

## 二、窗口大小一览

不同模型的窗口差异很大，且在快速扩大：

| 模型 | 上下文窗口 | 约等于 |
| --- | --- | --- |
| GPT-4o | 128K Token | ~10 万字 |
| DeepSeek R1 | 128K Token | ~10 万字 |
| GPT-5 | 400K Token | ~30 万字 |
| Claude Sonnet 4 | 1M Token | ~80 万字 |
| Gemini 2.5 | 1M Token | ~80 万字 |
| Llama 4 | 1M-10M Token | 数百万字 |

直观感受：128K Token 大约是一本中等长度的小说；1M Token 大约是一部长篇系列丛书。

## 三、上下文是如何被消耗的

一个常见误区是"窗口 8K = 我能问 8K 的问题"。实际上提示词和回答**共享**同一个窗口：

```
示例：窗口 8,000 Token
├── 系统提示词     1,000 Token
├── 你的提问       2,000 Token
├── 模型的回答     1,000 Token
└── 剩余可用       4,000 Token
```

由此推出两个重要结论：

1. **提问越长，留给回答的空间越小**。贴入大段资料后再要"写一篇长文"，可能两头都放不下
2. **多轮对话是累积的**。第 N 轮对话时，前面所有轮次的问答都还在窗口里占位置，直到超限被截断

## 四、实用策略

### 4.1 重要信息放前（或放后）

模型对窗口内信息的注意力并不均匀：**开头和结尾的内容利用率高，中间部分容易被忽略**（即 "Lost in the Middle" 现象）。长提示词的组织原则：

- 最重要的指令放在开头
- 参考资料、次要细节放中间
- 复述关键要求或输出格式放在结尾

### 4.2 控制长度、精简内容

- 粘贴资料前先删掉与任务无关的部分，比"全都塞进去让模型自己挑"更省、更准
- 要求长回答前先估算空间：`资料 Token 数 + 期望回答 Token 数 < 窗口大小`
- 明确限定回答长度（如"用 500 字以内总结"），避免回答挤占后续轮次的空间

### 4.3 超长内容的处理方式

当内容远超窗口时，不能硬塞，常用手段：

| 手段 | 做法 | 适用场景 |
| --- | --- | --- |
| 分块（Chunking） | 把长文档切成小块，分批处理再汇总 | 整本书的分析 |
| 摘要压缩 | 让模型先总结前文，用摘要替代原文续聊 | 超长多轮对话 |
| 检索增强（RAG） | 只把与问题最相关的片段检索出来注入窗口 | 知识库问答 |
| 外部记忆 | 把关键信息存到外部（文件、数据库），需要时再读入 | Agent 长期任务 |

RAG 的原理见 [向量化（Embedding）](04-embedding.md)。

### 4.4 长上下文 ≠ 好记性

即使窗口够大，模型对超长上下文的利用率也会下降（大海捞针能力随长度衰减）。所以：

- "窗口 1M" 不等于"可以无脑塞 1M"
- 能精简的精简，能检索的检索，**精准的上下文胜过海量的上下文**

## 小结

- 上下文窗口 = 模型的短期记忆，以 Token 计量，**提示词、注入资料、模型回答共享同一个窗口**
- 提问越长留给回答的空间越小；多轮对话累积占用，直到截断
- 重要信息放首尾，中间放次要内容（对抗 Lost in the Middle）
- 超长内容用分块、摘要、RAG、外部记忆来处理，精准优于海量
